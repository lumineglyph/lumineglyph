# ADR-002: Content Security Policy as an Astro-generated meta tag plus a CloudFront header

- **Status:** Accepted
- **Date:** 2026-11-13 (decided); 2026-11-15 (meta tag implemented in step 02; the header comes in step 05)

## Context

The main defence against injected scripts (XSS) is a "Content Security Policy" (CSP), which tells the browser the scripts, styles, fonts, and images a page is allowed to load. Securityheaders.com and Lighthouse check for a CSP.

This site is static (S3 + CloudFront), so there are no server code requests. In the static pages, Astro has inline `<script>` and `<style>` elements that differ per page and per build. A strict CSP must only allow those inline blocks.

There are a few ways to allow specific inline code:
- `'unsafe-inline'` -- allows any inline script, including injected ones (not safe).
- Nonces -- a random value per response. This needs a server to rewrite every response, which would require at least Lambda functions, increasing the cost, latency, and complexity to an otherwise simple, fast, and cheap site.
- Hashes -- a `sha256-...` of each inline block. These are good for static builds as the content is fixed.

A CSP can be delivered as an HTTP header or a `<meta http-equiv="content-security-policy">` tag. A meta tag can't carry some directives: `frame-ancestors` (who may embed the site), `report-uri`/`report-to`, and `sandbox`.

## Decision

1. **The page policy is a meta tag generated by Astro** (`security.csp` in `astro.config.mjs`). On each build, Astro hashes every script and style it outputs and writes a meta tag per page:
   - `script-src 'self' 'sha256-…'` and `style-src 'self' 'sha256-…'`
   - `default-src 'self'`, `img-src 'self' data:`, `font-src 'self'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'none'`
2. **A CloudFront response-headers policy (step 05) adds what a meta tag can't:** a CSP header with `frame-ancestors 'none'`, plus HSTS, `X-Content-Type-Options`, `Referrer-Policy` and `Permissions-Policy`.
3. **The header CSP must not contain `script-src`, `style-src` or `default-src`.** When a page has two policies, the browser enforces both, and a resource must pass each one. A header `default-src 'self'` without the build's hashes would block the inline scripts the meta tag allows.

To keep the policy this strict, the site was changed to need nothing else:
- No inline `style="…"` attributes and no `onerror=` handlers (both removed in step 01).
- Fonts are self-hosted, so the policy doesn't list Google's domains.
- Vite is told never to inline fonts as `data:` URIs, so `font-src` stays `'self'`.
- The small script that applies saved preferences before the first paint is a same-origin file (`/prefs.js`), not inline code.

## Consequences

**Positive**
- No `'unsafe-inline'` anywhere, and no third-party origins. Tested in step 02: an inline script injected into the live page was blocked, and the violation was logged.
- Hashes are regenerated on every build, so the policy can't drift out of sync with the code.
- No edge compute: the policy is part of the static files.

**Negative / trade-offs**
- **The policy is split between two places** (`astro.config.mjs` and the Terraform for CloudFront), and they must not overlap. Comments in both point here.
- **Astro inserts the meta tag after the page's own `<head>` elements.** The icons, the font preload and `/prefs.js` load before the policy applies. They're all static, same-origin files from the build, so nothing an attacker can influence comes before the tag.
- **The CSP isn't applied by `astro dev`.** Test it with `npm run build && npx astro preview`.
- **Anything new from another origin needs a policy change first**, such as analytics, an embedded Google Form or a video. Otherwise it's silently blocked.
- **Some Astro features don't work with this CSP**, for example `<ClientRouter />` view transitions and Shiki syntax highlighting. The site uses neither.
- **No violation reporting yet.** `report-to` needs the header and an endpoint to receive reports. It's a possible later addition in step 08.
